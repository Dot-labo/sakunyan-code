## Context

- pi はセッションを `~/.sakunyan/sessions/<作業フォルダ>/<日時>_<id>.jsonl` に保存する。1 行目はヘッダー（`type: "session"`、`id`、`cwd`）で、メッセージは `type: "message"` の行に入っている。
- `src/extension.ts` の動きは次のとおり。
  - `session_start` で、接続確認（`setupModel`）を行う。
  - `before_agent_start` で、system prompt を「pi の基本 → 応答モード → 実行環境 → 教室ルール」の順に組み立てる。
  - 古い ctx を使わないよう、世代やフラグでガードしている。
- 前の試作（`backup/issue-5-session-memory`）では、エピソード記憶だけの 1 層を作り、実機で 6 回の試用ループを回した。そこで分かった失敗とその対策を、この設計にすべて引き継ぐ（決定 8）。

## Goals / Non-Goals

**Goals:**

- 処理を「要約」と「畳み込み」の 2 つだけにし、記憶の層を 2 つだけにする
- 畳み込みでデータを失ったり、二重に反映したりしない
- 1 日 $0.1 の利用制限の中で、記憶のための追加費用を小さく抑える

**Non-Goals:**

- AGENTS.md のような手で書くファイル、過去の記録の検索ツール、記憶を編集する UI
- 前の試作の `summaries.json` の移行（新しいファイルを使い、古いファイルは読まない）

## Decisions

### 1. 分量（deepseek-v4-flash と 1 日 $0.1 から決める）

試作のログから、次のように見積もった。

- 普段の応答 1 回は、入力が約 2,600 トークン、費用が約 $0.0005〜0.0008。
- 要約 1 回は、入力が約 1,200 トークン、出力が 65 トークン、費用が約 $0.00016。
- 費用の多くは出力トークンで、入力の単価は低い。

記憶は質問のたびに、ツールを使う往復ごとに入力へ足される。そこで、上限を「普段の入力の半分以下」にする。

| 項目 | 上限 | 理由 |
|---|---|---|
| エピソード | 5 件 × 150 文字 | 試作で、前回の続きを把握するのに足りていた |
| 意味記憶 | 800 文字（テーマ 5 件、つまずき 3 件、傾向 3 件） | 5 テーマあれば、初学者が並行して学ぶ範囲をおおむね覆える |
| 見出しと決めつけを防ぐ一文 | 約 150 文字 | |
| 合計 | 約 1,700 文字（約 1,000〜1,200 トークン） | 普段の入力の約 4 割。費用は 1 回あたり +$0.0001 前後（推定） |

記憶は会話の途中で変えないので、system prompt の前半が会話の中で同じになり、プロバイダのプロンプトキャッシュが効きやすい。畳み込みは、普段は起動 1 回につき多くても 1 回（約 $0.0003 と推定）で済む。

### 2. 保存は 1 つのファイル

`~/.sakunyan/memory/memory.json` に、次の形で保存する。

```ts
{
  formatVersion: 1,
  episodes: [{ sessionId, timestamp, sessionModified, summary, summaryVersion, foldedRevision? }],
  semantic: { semanticVersion, revision, updatedAt, topics: [...], struggles: [...], habits: [...] } | null
}
```

畳み込み済みの印（`foldedRevision`）と意味記憶を同じファイルに入れる。こうすると「新しい意味記憶の保存」と「畳み込み済みの印」が、1 回の rename で一緒に反映される。ファイルを 2 つに分けると、片方だけが反映される瞬間ができてしまうので、分けない。

### 3. 要約（前の試作をそのまま引き継ぐ）

- ファイルの一覧を作るときは、`readdir` と `stat` で mtime を取り、新しい 50 件だけを候補にする。候補は、まずヘッダー（先頭 4KB）だけを読む。
- 要約できる条件、要約が必要な条件、1 回の起動で最大 5 件までという上限は spec のとおり。
- 前の試作では「注入に使う範囲だけを要約する」ことにしていた。今回は意味記憶に畳み込むので、古いセッションも要約する意味がある。そこで、範囲を打ち切らずに、新しい順に 1 回 5 件ずつ処理する。
- 畳み込み済みのエピソードは、版が古くても要約し直さない。中身はもう意味記憶に入っているので、作り直すと二重に反映されてしまう。
- 版だけが古い、畳み込んでいないエピソードは、要約し直すまでは注入にも畳み込みにもそのまま使う。最初は注入から外していたが、試用で版を上げたところ、要約し直すまで（1 回 5 件ずつ）その内容がどこにも見えなくなった。
- 要約する順は、未要約・再開されたもの → 版だけが古いもの → 版だけが古い「なし」とする。版を上げた直後に、新しい会話の要約が後回しにならないようにするため。
- 再開されたセッションは要約し直し、`foldedRevision` を消して、畳み込んでいない状態に戻す。

### 4. 畳み込み

- **条件**: 畳み込んでいない「なし」以外のエピソード（版は問わない）が 5 件を超えたら、古い順に、5 件を超えた分（最大 10 件）を選ぶ。
- **入力**: 今の意味記憶（JSON）と、選んだエピソード（古い順、日付付き）。
- **出力**: 新しい意味記憶の JSON。テーマ・つまずき・傾向の全部を返させる。
- **指示**:
  - 今の内容と新しいエピソードを合わせて、決めた形と分量に収める
  - テーマは言語や作品ごとに分け、同じテーマはまとめる。見送ったものも状態を「見送り」にして残す（例を付ける）
  - 進み具合は、最初から学んだ範囲を通して書く。長くなりそうなら、古い細かい項目をまとめて短くする
  - 次にやることや予定は書かない
  - エピソードにないことは書かない
  - 評価や助言は書かない
  - 古くて重要でない「一区切り」「見送り」のテーマから省く
- **検証**: JSON として読めるか、各区分の件数と文字数、状態の値、整えたあとの 800 文字、秘密情報を調べる。
- **1 回だけ直させる**: JSON として読めるが決まりに合わない場合は、合わないところ（例: 「『Python』の progress が 110 文字です（最大 100 文字）」）と前回の出力を元の入力に足して、1 回だけ直させる。それでも合わなければ、その回の畳み込みは捨てる。試用では、進み具合が学ぶほど長くなって上限を超え、3 回続けて捨てられた。直させずに捨てるだけだと、畳み込みが永久に失敗し続ける。
- **意味記憶に「次にやること」を持たせない**: 最初は各テーマに持たせていたが、試用で 3 回続けて、記録にない予定や、とうに終わった予定が書かれた。次にやることは新しいほど正しいので、最近の学習（エピソード）に任せる。
- **反映**: ロックを取ってから最新のファイルを読み直し、次の 2 点を確かめる。
  - `semantic.revision` が、畳み込みを始めたときと同じ
  - 選んだエピソードが、まだ畳み込んでいない状態で、`sessionModified` も同じ

  両方が成り立つときだけ、`revision + 1` の意味記憶と、選んだエピソードの `foldedRevision` を、1 回の書き込みで保存する。成り立たなければ何も書かない（楽観的な排他制御）。
- **繰り返し**: 1 回の裏の処理の中で、5 件以下になるまで繰り返す。ただし、失敗したらその起動では止める。

### 5. 意味記憶の版

意味記憶の形や畳み込みの指示を変えたときは、`SEMANTIC_VERSION` を上げる。版が違う意味記憶を読んだら、意味記憶を空にし、すべての `foldedRevision` を消してから畳み込み直す。残っているエピソード（最大 200 件）から作り直されるので、利用者が手で何かをする必要はない。

### 6. 注入（最初の質問で固定する）

- `session_start` で、記憶の文章のキャッシュを空にする。
- 各セッションで最初の `before_agent_start` のときに、`memory.json` を読んで記憶の文章を組み立て、キャッシュに入れる。残りの質問では、キャッシュの文章をそのまま使う。
- 組み立てる順番は、次のとおり。

  ```
  <pi の基本>

  <記憶の文章>
    ## 学習の全体像
    （テーマ: - Python（学習中）: 進み具合。次は〜 ／ つまずきやすい点 ／ 学び方の傾向）
    ## 最近の学習（新しい順）
    - 10/14: …
    （決めつけず、利用者に確かめるよう求める一文）

  <応答モード>

  <実行環境>

  <教室ルール>
  ```

- 「先頭」は、pi の基本（ツールの説明を含む）の後ろ、sakunyan が足す指示の先頭と解釈した。pi の基本より前に置くと、ツールの説明より前に学習の記録が来てしまい、指示の流れが崩れる。また、モードの指示と教室ルールを記憶より後ろに置くことで、記憶に命令のような文が混ざっていても、後から来るルールが優先されやすくなる。

### 7. 世代と並行の実行

`session_start` と `session_shutdown` で世代を進める。保存する直前に世代を確かめ、古ければ捨てる。同時に動く裏の処理は 1 本だけにする。接続確認と並行して始め、接続確認が成功したらもう一度呼ぶ（実行中なら何もしない）。

### 8. 前の試作から引き継ぐ失敗と対策

| 試作で起きたこと | この設計での対策 |
|---|---|
| 起動のたびに古い会話までさかのぼって要約し、呼び出しが増えた | 1 回の起動で 5 件まで、候補は新しい 50 件まで |
| 1 往復だけの会話（記録の読み上げ、あいさつ、使い方の質問）が要約され、前回の記憶を言い直すだけの自己強化が起きた | 利用者の発言 2 回以上、正常な応答 1 回以上 |
| 要約がエラーの応答に引きずられ、あいさつを返した | エラーで終わった応答は入力に入れず、条件にも数えない |
| 評価を盛る、第三者の視点で書く、助言の口調になる、sakunyan の勘違いを事実として書く | 要約の指示（主語、事実だけ、推測を書かない、例を付ける） |
| 要約の先頭に「利用者:」が付いた | 話し手の名前を取り除く |
| 長い要約が文の途中で切れた | 最後の「。」で切る |
| 要約を「理解済み」と言い換えた。どの話の続きかを決めつけた | 注入する文章に、決めつけず確かめるよう求める一文を入れる |
| 要約の作り方を変えても、古い要約が残って注入された | 要約の版。版が違う、畳み込んでいないエピソードは注入せず、要約し直す |
| 最初の質問に、直前の会話の要約が間に合わない | 接続確認と並行して始め、最初の質問のときに組み立てる |
| テストの fake の ctx に `getSessionFile` がなく、起動処理が落ちた | 裏の処理の準備段階のエラーも飲み込む |
| 日付の表示がタイムゾーンで変わる | テストではタイムゾーンを固定する |

今回の実機での試用（13 回）で、さらに次のことが分かった。

| 試用で起きたこと | 対策 |
|---|---|
| 要約がつまずきを落とし、「理解した」と盛った | つまずきは必ず書き、「理解した」は自分で書けた・動いた場合だけ書く |
| 次にやることが言い換えられた（「辞書」→「辞書内包表記」） | 会話の言葉どおりに書く |
| 版を上げると、要約し直すまでその内容が見えなくなった | 版が古くても、要約し直すまでは使う |
| 意味記憶の「次にやること」に、記録にない予定や終わった予定が入った | 意味記憶から「次にやること」をなくした |
| 見送ったテーマ（JavaScript）が、テーマとして残らなかった | 言語・作品ごとに分け、見送りも残すよう指示し、例を付けた |
| 進み具合から古い範囲が消えた | 最初から通して書き、長いときはまとめるよう指示した |
| 進み具合が上限を超え続け、畳み込みが永久に失敗した | 合わないところを伝えて、1 回だけ直させる |

さらに、判断の難しい会話 8 件を 3 回ずつと、21 件・8 テーマの長い流れを 3 回ずつ、要約と畳み込みの処理だけを本物のモデルで動かして確かめた（sakunyan の画面は起動しない検証用の仕組み）。そこで分かったこと:

| 試用で起きたこと | 対策 |
|---|---|
| 「なし」にした理由の文が、要約として保存された | 「なし」の 2 文字だけを返させ、理由の文はプログラムでも「なし」に直す |
| 相談してコードを受け取っただけの会話が、回によって要約されたり「なし」になったりした | 「〜を相談し、コードを受け取った（まだ試していない）」と書くよう例を付けた |
| インストールのトラブルが、テーマや「つまずきやすい点」になった | 環境やツールのトラブルはテーマにもつまずきにもしない（例を付けた） |
| sakunyan の説明のまちがいや、記録にないことが「つまずきやすい点」になった | 利用者自身のつまずきとして記録にはっきり書かれたものだけにする |
| 「次にやることは決まっていない」という中身のない文が入った | プログラムで取り除く |
| テーマ名が「リスト」「Pythonクラス」のように細かくなり、別のテーマになった | 要約の入力に、これまでのテーマ名を添えて使わせる |
| テーマの状態（学習中・一区切り・見送り）が回によってぶれた | 要約で、終わりにした・やめたときだけ印を付けさせ、状態はプログラムが一番新しい記録の印で決める |
| 古い会話があとから畳み込まれ、一区切りが学習中に戻った（プログラムのまちがい） | 前の全体像のほうが新しい記録をもとにしていれば、前の状態を使う |
| 返答で、記憶を sakunyan 自身の学習のように話したり、✅ で理解済みのように示したりした | 注意書きに「利用者の学習記録で、sakunyan 自身のことではない」「✅などで示さない」を加えた |
| テーマが 5 件を超えたとき、学習中のテーマ（Git、HTML/CSS）が捨てられ、見送ったテーマが残った（3 回中 2 回） | 要約にテーマ名を付け、残すテーマはプログラムが「状態 → 最後に学んだ日」の順で決める。モデルが書き忘れたテーマは前の内容で戻し、新しいテーマが抜けたら直させ、それでも抜けたら要約から 1 行作る |

## Risks / Trade-offs

- [最初の質問より要約が遅いと、直前の会話はそのセッションに入らない] → 待たないことを優先する。次のセッションには入る
- [畳み込みで、モデルが細かい内容を落とす] → 分量の制約による意図した圧縮として受け入れる。エピソードとセッションのログは残すので、版を上げれば作り直せる
- [畳み込みが続けて失敗すると、エピソードが 5 件を超えて溜まり、入力が増える] → 起動のたびに再試行する。spec のとおり、あふれた分も外さない
- [再開されたセッションを畳み込み直すと、同じ内容が意味記憶に二重に入りうる] → 畳み込みの指示で「同じテーマはまとめる」とする。頻度が低いので受け入れる

## Migration Plan

新しいファイル `memory.json` を使い、前の試作の `summaries.json` は読まない。初めて起動したときに、新しい順に 5 件ずつ要約が作られる。エピソードが 5 件を超えると、意味記憶ができる。元に戻すときは、extension.ts のつなぎ込みを外せばよい。
