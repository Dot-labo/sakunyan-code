## Context

現在のpi拡張は `src/extension.ts` でセッション開始とターン・ツール実行のイベントを受け、`ctx.ui.setStatus` による状態表示を更新している。教育用プロンプトは `src/educational-prompt.ts` からCLIの `--append-system-prompt` へ固定で渡され、slash command と応答モードの状態は存在しない。Issue #4 ではモードの表示情報とプロンプトを1か所で管理し、選択したプロンプトを次のターンへ適用できる基盤を追加する。

## Goals / Non-Goals

**Goals:**

- pi標準の拡張APIで `/mode` とキーボード操作可能な選択UIを提供する
- 各モードを識別子、日本語を扱える表示名、説明、注意点、プロンプトの最小データで表し、1ファイルで編集できるようにする
- 現在モードをセッション内で保持し、既存の状態表示と一緒に常時確認できるようにする
- 選択したモードのプロンプトを次のユーザーメッセージから適用する
- 定義、選択、確定、キャンセル、プロンプト適用と既存イベントの回帰を自動テストする

**Non-Goals:**

- 具体的なモード名や個数を仕様として固定すること
- 具体的なプロンプト本文やモード別のツール、権限、モデルの変更
- AIによる自動切り替え、ショートカット、セッションをまたぐ永続化
- 将来向けのモードレジストリ、クラス、外部設定ローダーを先に作ること

## Decisions

### piの `registerCommand` と `ctx.ui.custom` をそのまま使う

`/mode` はpi標準の `registerCommand` で登録し、選択画面は既存のAPIキー入力でも使っている `ctx.ui.custom`、`matchesKey`、`truncateToWidth` で実装する。選択位置は画面内の数値として持ち、矢印キーで循環させる。追加のUIライブラリや汎用コンポーネントは作らない。

代替案としてpiの単純な選択APIもあるが、選択中の説明と注意点を同時に表示する要件を満たしにくいため採用しない。

### `src/modes.ts` をモード定義の単一の編集箇所にする

`src/modes.ts` に、安定した識別子、UTF-8の表示名、説明、注意点、複数行プロンプトを持つ読み取り専用の配列と既定モードIDを置く。既存の教育用プロンプトもこの定義へ移し、モードを追加・修正するときの編集箇所を1ファイルにする。TypeScriptの文字列は日本語をそのまま保持でき、型検査も使えるため、JSON・YAMLのパーサーや独自ローダーは追加しない。変更は通常のビルド後に反映される。

現在値は拡張内の変数で保持し、セッション開始時に既定値へ戻す。具体的な表示値、件数、プロンプト本文は実装データとし、この変更の仕様契約にはしない。

代替案の「モードごとに別ファイル」はファイル探索と解析が必要になり、定義全体も見渡しにくくなるため採用しない。永続ストレージや汎用状態管理も追加しない。

### `before_agent_start` で選択中のプロンプトを適用する

CLIから固定の教育用プロンプトを渡す処理を外し、pi標準の `before_agent_start` で、その時点のシステムプロンプトへ現在モードのプロンプトを追加する。これにより、モード確定後の次のユーザーメッセージから選択内容が反映され、pi本体が生成する基礎プロンプトや既存のコンテキストは維持される。

会話履歴を書き換えたり、モード変更用メッセージをLLMへ挿入したりはしない。ツール、権限、モデルの切り替えは後続Issueの責務とする。

### 既存の状態表示更新を1か所に集約してモード名を付ける

現在は各イベントが `setStatus` を直接呼ぶため、共通の小さな表示関数を経由させ、待機中・処理中の文言と現在モードを同じ状態行へ出す。これによりターン開始やツール実行でモード表示が消えることを防ぐ。モード確定時は同じ関数で状態行を更新し、`ctx.ui.notify` で結果も通知する。

独自フッターへの全面置換は、既存のpi表示を壊す範囲が広いため行わない。

### 確定するまで現在値を変更しない

選択画面は開始時に現在モードを指す。矢印操作は画面内の候補だけを変え、Enterで初めて現在値を更新する。EscまたはCtrl+Cでは値と通知を変更せず終了する。モード変更後もツール、権限、モデル、会話履歴には触れない。

## Risks / Trade-offs

- [モード名を仕様化しないため、後続Issueで表示値が変わり得る] → テストは特定名称や件数ではなく、設定された定義の表示と選択結果を検証する
- [定義ファイルのID重複や存在しない既定IDで起動できなくなる] → 定義の一意性、必須項目、既定IDを小さな自動テストで検証する
- [既存の固定プロンプトを外すと既定モードへ移し忘れる可能性がある] → 既存プロンプト本文が既定モードへ含まれることをテストする
- [既存の状態行へモード名を追加すると狭い端末で表示が長くなる] → 簡潔な区切りで付加し、選択画面と同様に端末幅へ収める
- [状態をメモリだけに持つため再起動で戻る] → これはIssue #4の意図した非永続動作とし、永続化が必要になった時点で別途設計する

## Migration Plan

既存の教育用プロンプトを既定モードへ同内容で移すため、利用者のデータ移行は不要。問題があればコマンド登録、モード状態、状態行への付加、`before_agent_start` を戻し、CLIの固定プロンプト指定を復元すれば従来動作へ復帰できる。
