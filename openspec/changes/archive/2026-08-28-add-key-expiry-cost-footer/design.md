## Context

現在のTUI拡張は `ctx.ui.setHeader`、`ctx.ui.setStatus`、`ctx.ui.setWidget` を使ってヘッダー、状態、接続確認結果を表示している。接続確認結果は `aboveEditor` のウィジェットとして常時表示されるため、この行へキー情報を追加し、既存のフッター状態表示は変更しない。Node.js 22では追加ライブラリなしでHTTPリクエストを実行できる。

APIキーのメタデータは、OpenRouterのキー情報API（`GET https://openrouter.ai/api/v1/key`）から取得する。レスポンスの `data.limit_remaining`、`data.limit`、`data.expires_at` を表示用の安全な状態へ変換し、APIキー自体は画面・ログ・エラーメッセージに出さない。

## Goals / Non-Goals

**Goals:**

- 起動後の接続確認結果の行に有効期限と利用残量を常時表示する。
- 利用残量を固定幅のバーとパーセントへ変換し、端末幅が狭くてもレイアウトを崩さない。
- APIからの取得中、取得失敗、上限なしなどを誤解のない状態表示にする。
- セッション開始時に取得し、ターン終了後および一定間隔で再取得して表示を更新する。
- 取得処理と表示処理を分離し、日時・割合・警告状態を純粋な整形処理としてテスト可能にする。

**Non-Goals:**

- APIキーの発行、更新、削除、利用上限の変更。
- OpenRouter以外のプロバイダへの対応。
- 利用履歴や個別リクエストごとのコスト明細の表示。
- APIキーの保存形式や認証フローの変更。

## Decisions

- **OpenRouterのキー情報APIを利用する。** セッション内の累計コストだけではキー全体の残量や有効期限を表せないため、認証済みキーで `/api/v1/key` を呼び出す。piのモデルレジストリから実行時のAPIキーを取得し、認証情報を別形式で複製しない。独自のローカル推定やセッション使用量だけの表示は、他のセッションの利用を反映できないため採用しない。
- **表示状態を専用の型に正規化する。** APIレスポンスをそのままUIへ渡さず、`expiry`、`remainingPercent`、`remainingAmount`、`status` のような表示用データへ変換する。`limit` または `limit_remaining` が欠落・不正な場合は割合を計算せず、バーとパーセントに推測値を表示しない。
- **残量割合は残額を基準にする。** `limit_remaining / limit * 100` を0〜100に収め、小数点以下を丸めて表示する。バーは固定幅の塗りつぶし文字と空き文字で描画し、パーセントと同じ正規化済みの値を使う。上限が設定されていない場合は「上限なし」、情報を取得できない場合は「取得できません」と表示する。
- **有効期限は相対情報だけを簡潔に表示する。** 24時間以上は日、24時間未満は時間、1時間未満は分の単位で「あとN日」「あとN時間」「あとN分」と表示する。未期限の場合は「期限なし」、不正値や欠落時は「取得できません」、期限切れは「期限切れ」とする。期限まで7日以内または期限切れの場合は注意色にする。
- **接続確認結果の行へ簡潔なキー情報を追加する。** `接続確認OK 🔑 あとN日 [バー] ...%` のように、接続確認メッセージ、絵文字、残り時間、バー、パーセントだけを1行で表示する。ラベルや絶対日時は省略し、既存の待機中フッター `🐱 質問を入力してね...` はpi標準の状態表示として残す。通常表示は既存の日本語UIの `success`、注意状態は `accent` または `error` を使い、`NO_COLOR` 時も文字情報だけで意味が伝わるようにする。
- **取得はUI表示と分離し、ウィジェットを更新する。** `setWidget` 内ではネットワーク処理を行わず、状態更新後に接続確認結果のウィジェットを差し替える。初回表示は「接続確認OK 🔑 取得中…」、取得失敗時は最後の正常値を保持せず「接続確認OK 🔑 取得できません」とする。セッション開始時、各ターン終了時、約60秒ごとに取得し、タイマーを解除する。既存の状態表示用フッターは `setStatus` に任せる。
- **秘密情報を保護する。** HTTPリクエストのAuthorizationヘッダーは取得処理のスコープ内だけで使い、APIキーを表示用状態、ログ、通知、例外文へコピーしない。APIエラーは内部の詳細を表示せず、フッターには取得失敗の固定メッセージだけを表示する。

## Risks / Trade-offs

- [OpenRouterのキー情報APIが利用できない、またはレスポンス形式が変わる] → タイムアウトとレスポンス検証を設け、検証できない値は表示せず「取得できません」とする。API呼び出しの失敗は通常のモデル利用を妨げない。
- [各ターン終了後の取得で通信量や待ち時間が増える] → フッター更新は非同期で行い、モデル応答を待たせない。60秒の間隔とターン終了時の更新を併用し、同時リクエストは1つに制限する。
- [狭い端末で有効期限、バー、状態表示が切れる] → 2行レイアウト、表示幅計測、切り詰めを使い、期限行ではパーセントを優先する。
- [メタデータAPIへの認証情報が漏れる] → APIキーを状態やメッセージへ含めず、例外内容も利用者へ転送しない。テストでは実キーを使わず、HTTPクライアントを差し替えて検証する。

## Migration Plan

1. キー状態の型、OpenRouterメタデータ取得、簡潔な表示整形を追加する。
2. TUIの接続確認結果ウィジェットへ表示を追加し、ターン終了・タイマーの更新処理を接続する。
3. APIキーが設定済みの環境、未設定の環境、期限・残量情報を取得できない環境でテストする。
4. 通常のモデル接続や既存のAPIキー保存形式に影響がないことを確認してリリースする。
5. 問題がある場合は接続確認結果ウィジェットへの追加表示とメタデータ取得呼び出しを取り除けば、既存のヘッダー・ステータス表示へロールバックできる。
