## 背景

現在の `cli.ts` はpiを起動するだけで、OpenRouterのモデル指定やAPIキー未設定時の案内を行っていない。`extension.ts` はTUIのヘッダーと状態表示を設定しているため、起動後の疎通確認と生徒向けの入力案内はこの起動経路に追加する。

利用するプロバイダはOpenRouter、モデル識別子は `deepseek/deepseek-v4-flash` に固定する。これらの指定値は専用の設定モジュールにまとめ、起動処理と接続確認が同じ定義を参照する。

## 目的・対象外

**目的:**

- 起動時に固定モデルで応答可能かを確認する。
- APIキーが未設定または無効な場合、先生から受け取ったキーを入力するよう日本語で案内する。
- 入力後に同じ固定モデルで接続を再確認し、成功したら通常の入力待ちへ進む。
- APIキーをログやエラーメッセージに表示しない。入力中のAPIキーは確認のため画面に表示する。
- 有効なAPIキーを再起動後も利用できるようにする。

**対象外:**

- 生徒がプロバイダやモデルを選択・変更する機能。
- 複数プロバイダ、複数モデル、モデル選択UI。
- 独自のAPIキー保存形式やアカウント管理。

## 判断

- **固定設定は1つの設定モジュールで管理する。** プロバイダとモデル識別子を専用の設定モジュールに定義し、`cli.ts` の起動引数と接続確認の両方から参照する。値の重複を避け、モデル変更時の修正箇所を1か所にする。
- **固定設定は起動引数で渡す。** 設定モジュールの値から `--provider` と `--model` を組み立ててpiへ渡し、pi標準のモデル解決を使う。
- **起動確認は拡張のセッション開始処理で行う。** 現在のTUI拡張のライフサイクルに接続し、固定モデルへの最小リクエストを実行する。成功時は通常画面へ、失敗時はセットアップ状態へ進める。
- **APIキー入力はpiのUI入力を使う。** `ctx.ui.input` を使って入力を受け、入力値をpiのOpenRouter認証へ反映してから再確認する。専用の入力コンポーネントや新規依存は追加しない。
- **APIキーはpi標準の認証ファイルへ保存する。** 接続確認に成功したキーだけを `~/.pi/agent/auth.json` のOpenRouter認証情報として保存し、次回起動時はpiの標準認証読込に任せる。
- **認証失敗時は同じセットアップ状態を再利用する。** 入力欄にはキーを表示し、ログやエラー文には出さず、再入力を促す。キャンセルまたは終了操作では起動を継続せず、明示的に終了できるようにする。

## リスク・トレードオフ

- [APIキー入力後も認証状態の同期に失敗する可能性] → piの標準ランタイム／認証APIを使い、設定反映後に必ず再疎通する。
- [起動時の疎通確認でネットワーク待ちが発生する可能性] → 起動中であることを状態表示し、失敗時は入力案内へ切り替える。
- [APIキーを永続保存しないため毎回入力が必要になる可能性] → 今回は独自保存を行わず、pi標準の認証保存機能を利用できる範囲に限定する。永続化要件が確定したら別変更で扱う。
