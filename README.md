# 生徒向けコーディングエージェント(sakunyan-code)

プログラミング教室の生徒が、課金の壁なく自由に使えるコーディングエージェント環境。
OpenCode を無改造のまま活用し、認証・コスト管理・教育的な振る舞いを外付けする。
**二段階で開発する**: まず OpenRouter 直叩きの最小構成で配布し(Phase 1)、その後プロキシを挟んでトラッキング・ルーティング・教育効果測定をサーバ管理に移行する(Phase 2)。

---

## 背景

- 教室では生徒にコーディングエージェント(Claude Code / Codex 等)を自由に使えるようになってほしいが、これらの本格利用は有料プランが前提であり、ほとんどの生徒は無料枠の中で工夫して使っている状況。
- 生徒はクレジットカードを持てないため、個人での課金は現実的でない。
- 生徒は全員、会社が開発した Web アプリのアカウント(Supabase で管理)を既に保有している。

## 目的

1. **生徒が実質無制限にコーディングエージェントを使える体制をつくる**
   裏側ではコスト上限とモデル選択で制御するが、生徒はモデルや料金を意識しない。
2. **教育的に振る舞うエージェントをデフォルトにする**
   実装を全部代行するのではなく、先生・師匠のように問答で理解を深める「Coach」を標準にする。
3. **利用状況を教室側で把握し、教育に還元する**(Phase 2)
   利用量・利用内容のトラッキング、モデルルーティング、教育効果の測定を運営側で行う。
4. **本物のツールへの"卒業"を前提にする**
   最終目標は、生徒が素の Claude Code / Codex / OpenCode を使っても戸惑わないこと。独自ツールへの囲い込みはしない。この方針が UI 設計(後述)にも反映されている。

## 二段階開発の方針

| | Phase 1(まず作って配布) | Phase 2(運用後に移行) |
|---|---|---|
| LLM への経路 | OpenCode → OpenRouter 直叩き | OpenCode → **自前プロキシ(LiteLLM)** → OpenRouter |
| コスト制御 | OpenRouter の per-key 月次上限 | プロキシの virtual key / budget 管理 |
| キー管理 | 生徒ごとに OpenRouter キーを発行・失効 | サーバに OpenRouter キー 1 本のみ(生徒キー発行は廃止) |
| 見える情報 | 使用量(金額・リクエスト数)のみ | 利用内容を含むログ |
| ルーティング | なし(固定モデル設定) | サーバ側で動的ルーティング(多量利用者を軽量モデルへ等) |
| 教育効果測定 | なし | ログに基づく測定(指標設計は着手前に行う) |

Phase 1 → 2 の移行は、クライアント配布物の baseURL をプロキシに差し替えるだけで完了する設計とする。クライアント側(npm パッケージ、Coach、プロファイル)は両 Phase で共通。

## 作るもの

### Phase 1

| # | 成果物 | 概要 |
|---|--------|------|
| 1 | キー発行 API(Supabase Edge Function) | 生徒の JWT を検証し、OpenRouter Management API で生徒専用キー(月次上限付き)を発行・失効 |
| 2 | npm ラッパーパッケージ(`@dotlabo/sakunyan-code` 仮) | OpenCode 同梱、`dotlabo login`(ブラウザ認証)、設定・エージェント定義・プラグイン・ツール一式の配置 |
| 3 | Coach エージェント定義(markdown 1 枚) | 教育的システムプロンプト+権限制約 |
| 4 | プロファイル用 custom tool | 生徒の興味・理解度・教育方針を記録したローカルファイルの読み書き |

### Phase 2

| # | 成果物 | 概要 |
|---|--------|------|
| 5 | LLM プロキシ(LiteLLM、VPS or Cloud Run) | Supabase JWT 認証、ルーティング、利用ログ、コスト管理を集約 |
| 6 | 利用状況ダッシュボード | 生徒ごとの利用量・利用傾向の可視化 |
| 7 | ルーティングポリシー | 使用量・タスク種別に応じたモデル振り分け |
| 8 | 教育効果測定 | 指標を 1 つに絞って設計(例: Coach の問答後に自力で書いたコードの割合、同一概念への質問頻度の推移)。ログスキーマは指標から逆算する |

OpenCode 本体のフォークは行わない(全 Phase 共通)。

## 技術選定

| 領域 | 選定 | 理由 |
|------|------|------|
| エージェント基盤 | OpenCode(無改造) | カスタムエージェント・カスタムツール・プラグイン・instructions・権限制御が標準機構で揃っており、要件のほぼ全てが設定+拡張で実現できる。フォーク不要のため upstream 追従コストがゼロ |
| LLM ゲートウェイ | OpenRouter | 複数モデルへの単一 API。Management(Provisioning)API によりユーザーごとのキー発行・支出上限・使用量計測がプラットフォーム側で完結する(Phase 1 の要) |
| プロキシ(Phase 2) | LiteLLM Proxy | virtual key・budget・ルーティング・ロギングが既製で揃っており、自作部分は JWT 検証程度で済む |
| 認証 | Supabase Auth(既存) | 生徒が既に持つ Web アプリのアカウントをそのまま利用 |
| キー発行基盤 | Supabase Edge Function | 既存の Supabase プロジェクトに同居でき、JWT 検証が自然に書ける |
| 配布 | npm パッケージ | Windows / macOS 両対応。生徒はターミナル操作が可能なため CLI インストールで足りる |

### 検討して見送った案

- **OpenCode のフォーク** — 日本語 UI やキャラクター表示のために本体改造すると upstream 追従に工数を取られ続ける。応答の日本語化・キャラクター性はエージェントのプロンプトで実現できるため不要と判断。
- **最初からプロキシ方式で作る** — トラッキング・ルーティングの自由度は最大だが、運用・可用性の責任を初日から負うことになる。まず直叩き構成で配布して運用実績とコスト実数を得てから移行する(本 README の二段階方針)。
- **pi をベースにする案** — TUI 自体を拡張したい場合の選択肢だったが、キャラクター性はプロンプト内で十分成立するため OpenCode を採用。

## アーキテクチャ

### Phase 1

```
┌──────────────────────┐
│ 生徒の PC (Win/Mac)   │
│                      │
│  @dotlabo/sakunyan-code      │ ← npm で配布
│   ├─ dotlabo login ──┼──→ ブラウザ → Supabase Auth
│   ├─ OpenCode(無改造)│         │ JWT
│   │   ├ Coach agent  │         ▼
│   │   ├ custom tool  │  ┌──────────────────┐
│   │   └ plugins      │  │ Supabase          │
│   └─ ~/.dotlabo/     │  │  Edge Function    │
│       profile.md     │  │  (JWT検証+キー発行) │
│                      │  └──────┬───────────┘
│                      │         │ Management API
│         │ 発行された生徒専用キー  ▼
│         └────────────┼──→ ┌──────────────┐
│                      │    │ OpenRouter    │
└──────────────────────┘    │  per-key 上限  │
                            │  使用量計測    │
                            └──────────────┘
```

### Phase 2(baseURL の差し替えで移行)

```
┌──────────────────────┐
│ 生徒の PC (Win/Mac)   │
│                      │
│  @dotlabo/sakunyan-code      │
│   ├─ dotlabo login ──┼──→ Supabase Auth(JWT 取得)
│   └─ OpenCode ───────┼──→ ┌────────────────────┐
│       (baseURL変更)   │    │ LiteLLM Proxy       │
└──────────────────────┘    │  JWT検証            │
                            │  ルーティング        │
                            │  利用ログ・コスト管理 │
                            └────────┬───────────┘
                                     │ OpenRouter キー1本
                                     ▼
                            ┌──────────────┐
                            │ OpenRouter    │
                            └──────────────┘
                            (生徒ごとのキー発行は廃止)
```

### 認証・キー発行フロー(Phase 1)

1. 生徒が `dotlabo login` を実行 → ブラウザが開き Supabase でログイン
2. Edge Function が JWT を検証し、OpenRouter Management API で「生徒 ID ラベル付き・**月次支出上限付き**(`limit_reset: monthly`)」のキーを発行
3. キーをローカルに保存。OpenCode はこのキーで OpenRouter を直接叩く
4. 再ログイン時は新キーを発行し旧キーを失効(漏洩対策を運用に織り込む)

### コスト制御(Phase 1)

- キーごとの月次上限を設定。**上限到達後のリクエストは OpenRouter 側でプロバイダ送信前に拒否される**ため、上限を超えた上流コストは発生しない。
- 使用量(日次/週次/月次)は Management API から取得でき、バッチで収集できる。
- 生徒にはモデル名や残量を意識させない。

## 教育設計

### Coach エージェント(デフォルト)

- `default_agent` を Coach に設定。起動した瞬間から教育モード。
- markdown エージェント定義(frontmatter + システムプロンプト)で実装。
- **教育的制約はプロンプトではなく権限で強制する**:
  - `edit` / `write` は deny(または ask)
  - `read` / `grep` / `glob` と限定的な `bash` のみ許可
  - → モデルの応答が長い対話で崩れても、構造的に「実装の丸投げ」ができない
- 実装が必要な場面では生徒が明示的に Build エージェントへ切り替える(この切り替え操作自体が OpenCode の標準操作の学習になる)。

### キャラクター

- キャラクターの人格・口調はすべて Coach のシステムプロンプトで実現(TUI 改造なし)。
- エージェントの `color` 設定で UI 上の視覚的区別をつける。

### 長期プロファイル

- `~/.dotlabo/profile.md` に生徒の興味・理解度・教育方針を記録。
- OpenCode の `instructions` に含めて毎セッション読み込み。
- 書き込みは custom tool(`profile_update`)経由で、Coach にのみ許可。
- Phase 1 ではローカル保存のみ(サーバには送らない)。

### 日本語と「卒業」のバランス

- エージェントの応答・説明・エラー解説は日本語。
- **TUI のメニュー・キーバインド表示は英語のまま**とする。Claude Code / Codex も英語 UI であり、ここに慣れることが卒業目標への資産になる。初回起動時に Coach が日本語で操作方法を案内することで補完する。

## リスクと対策

| リスク | 対策 |
|--------|------|
| Windows での OpenCode の動作不安定 | **最優先で検証する**(構成全体の前提。着手前に代表機で一通り確認) |
| ローカル保存キーの漏洩(友達に共有、GitHub に push 等) | 月次上限で被害額を限定+ログインし直しで旧キー即失効の運用。Phase 2 移行で生徒キー自体が消滅 |
| 子供が Build エージェントで危険なコマンドを許可してしまう | `rm` 系・想定外パスへの書き込みを deny に倒した権限プロファイルを配布設定に含める。保護者説明にも明記 |
| プロンプトだけの教育的制約は長い対話で崩れる | 権限レベルでの強制(上述)を本命とする |
| CLI のブラウザ認証フロー(PKCE+コールバック)の実装が膨らむ | Phase 1 で最も工数リスクの高い箇所と認識して着手。詰まった場合の逃げ道として「Web アプリ上でキーを表示→CLI に貼り付け」方式に一時フォールバック可能な設計にする |
| Phase 2 のログが「溜めただけ」で死蔵する | 測定指標を 1 つに絞ってからログスキーマを設計する(逆順にしない) |

## データの扱い

- **Phase 1**: 会社側が取得するのは使用量(コスト)のみ。会話内容はサーバを経由しない。生徒プロファイルはローカル保存。
- **Phase 2**: プロキシ経由となるため利用内容がログに残る。移行前に取得範囲・保存期間を明文化し、保護者への説明を更新する。
- 保護者への説明は会社側で実施する。

## ロードマップ

1. **検証**: Windows / macOS で OpenCode の動作確認(インストール〜日本語入出力〜bash ツール)
2. **Phase 1 実装**: Coach 定義+opencode 設定 → キー発行 Edge Function → `dotlabo login` → npm パッケージ化
3. **配布・運用**: 少人数の生徒で試験運用、月次上限の実数を調整、使い続けられるかを観察
4. **Phase 2 移行判断**: 運用実績とコスト実数が揃い、内容トラッキング・ルーティングの必要性が確認できたら着手
5. **Phase 2 実装**: 測定指標の決定 → LiteLLM プロキシ構築 → baseURL 切り替え → ダッシュボード・ルーティングポリシー → 保護者説明の更新
